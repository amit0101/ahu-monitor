How the Backend Works

Big picture first, then each stage in detail with its physical and mathematical formulation.

The big picture

The backend is a digital twin of one air-handling unit (AHU). The AHU is modelled as a graph of components (fans, coils, filter, damper), and each component has sensors.

There are two independent halves:

  • The simulator knows the ground truth. It produces sensor readings and injects faults that grow over time.
  • The analytics never see the ground truth. They see only the readings and each sensor's normal profile (μ, σ), and they have to work out what's going on.

On every tick, the analytics answer five questions in order:

1 · DetectIs this reading abnormal?
2 · AssessHow healthy is each component?
3 · DiagnoseWhich fault fits the pattern?
4 · PredictHow long until failure?
5 · ActIs it worth alerting someone?

0Making the data

Normal readings are noise around a mean. A fault is a hidden severity s(t) that rises from 0 to 1 and distorts specific signals.

Normal operation

Each sensor reading is Gaussian around its rated mean, plus a gentle daily cycle and an occasional spike:

x = N(μ, σ) + 0.5σ·sin(2π·day) + rare spike N(0, 2σ) (p = 0.5%)

Faults

Each fault has a severity curve. Its shape comes from the physics of the failure:

Faults(t)Why that shape
Bearing wearα(e^(βt) − 1)Fatigue spalling grows on itself: damage → more vibration → more damage
Filter cloggingεt^1.5The dust cake thickens, so resistance rises faster than linearly
Coil foulingδtFouling resistance builds up roughly at a constant rate
Belt slippageγt²Slow wear at first, then it accelerates

Severity is then mapped onto the signals, each with its own sensitivity k. Degraded parts also get noisier:

x' = x·(1 + k·s) + offset·s e.g. bearing: vibration ×(1 + 1.8s), temp +25s °C

The default run has three overlapping faults: filter (day 20), bearing (day 35) and coil (day 55). Overlapping faults are the hard case for diagnosis.

1Detect: is this reading abnormal?

Three detectors, each good at catching a different kind of change, are blended into a score in [0, 1].

A plain z-score threshold has two weaknesses. Set it tight and noise causes false alarms. Set it loose and it misses small, persistent shifts. So each sensor runs three detectors:

a) EWMA residual: sudden departures

A slow moving average follows the recent level. A reading far from that average is suspicious.

e ← 0.01·x + 0.99·e (memory ≈ 1/α = 100 samples) score_EWMA = |x − e| / 3σ

b) CUSUM: small shifts that persist

This is Page's cumulative sum. It adds up evidence that the mean has moved away from baseline. Deviations under the slack k are treated as noise and leak away. Anything larger keeps accumulating.

S⁺ = max(0, S⁺ + (x − μ) − k) k = 1σ S⁻ = min(0, S⁻ + (x − μ) + k) score_CUSUM = max(S⁺, |S⁻|) / h h = 5σ

For a sustained shift of δσ, the sum grows by about (δ − 1)σ per sample. So it reaches h after about 5/(δ − 1) samples: about 5 for a 2σ shift and about 25 for a 1.2σ shift. This is the detector that catches slow degradation.

c) Isolation Forest: unusual values without a Gaussian assumption

The forest is trained on the first 100 readings of each sensor. Values that random splits isolate in only a few cuts are rare. The raw score is scaled so the training median maps to 0.

Blend

score = clip( 0.7·max(EWMA, CUSUM) + 0.3·IF ) anomalous if > 0.5 signal_health = 1 − score

Taking the max means whichever of the two statistical detectors fires harder wins. The forest adds a smaller second opinion.

2Assess: how healthy is each part?

Average the sensors into a component health, then take a criticality-weighted average of the components for the whole AHU.

signal health→ mean →component health→ weighted mean →AHU health
H_component = mean(signal healths) H_AHU = Σ wᵢ·Hᵢ supply fan .35 · cooling coil .20 · filter .15 · return fan .15 · heating .10 · damper .05

Health then sets the state: ≥ 0.70 normal, 0.40 to 0.70 warning, < 0.40 critical. The weights reflect how much losing each part hurts the AHU. If the supply fan stops, nothing moves air.

3Diagnose: which fault is it?

Each fault has a fingerprint: a direction in signal space. Diagnosis picks the fingerprint the current deviations point towards.

Each component's readings become a z-vector over 7 signals: [vibration, acoustic, temp, current, ΔP, airflow, speed]. Every fault has a signature vector in the same space. For example, bearing wear is [3, 1.5, 2.5, .8, 0, 0, 0] and filter clogging is [0, 0, 0, 1, 3, −2, 0].

z = (x − μ)/σ per signal confidence = max(0, cos θ) = max(0, z·sig / (‖z‖‖sig‖)) diagnosed if ≥ 0.45 (θ ≲ 63°)

Why cosine: it compares direction and ignores magnitude. A fault in its first week and the same fault near failure point the same way, so severity doesn't change the diagnosis. The signatures are close to orthogonal (bearing · filter gives cos ≈ 0.05), which makes the faults easy to tell apart.

4Predict: how long until failure?

Fit a curve to the recent health trajectory and extrapolate to where it crosses the failure line.

This only runs once a component drops into warning (H ≤ 0.70). Only the most recent 30% of its health history is used, so the current trend dominates.

exponential: H(t) = a·e^(bt) + c (b ≤ 0: decaying) linear: H(t) = m·t + c → keep the fit with lower MSE; step forward 0.5 d (up to 180 d) RUL = first t where H(t) < 0.15

Two models are fitted because they disagree in a useful way. Exponential decay is usually the more pessimistic of the two, and it matches accelerating wear.

Failure probability is a logistic function of health, centred on the critical line, plus an urgency bump when RUL is short:

P = 1 / (1 + e^(6(H − 0.4))) + 0.3·(1 − RUL/30) if RUL < 30 d H = 1 → 0.03 H = 0.4 → 0.50 H = 0.15 → 0.82

5Act: is it worth alerting someone?

Alerts fire on real, sustained changes of state, not on single noisy ticks.

An alert needs all four of these to hold:

  • Training gate: day ≥ 20, so the detectors have learned what normal looks like.
  • Debounce: 5 consecutive ticks in warning or critical. This filters out blips.
  • Edge trigger: fire only when the state changes (normal→warning, warning→critical), not every tick.
  • Cooldown: at least 3 sim-days since this component's last alert.

Together these act like a Schmitt trigger: health hovering around 0.70 won't flood the operator with alerts.

Recommendations are sticky in the same spirit. One is raised the first time a component degrades with a recognised fault. It stays until the component is back to normal, and its priority (critical / high if RUL < 15 d / medium) is updated on every tick.

+Time

One tick is one sensor sample. The speed setting compresses wall-clock time.

Δday per tick = speed / (tick_hz · 86400) ticks per real second = speed · tick_hz

Both terms scale with speed, so sim time actually advances at speed². At 50× that's about 2500×, and the 90-day scenario takes about 52 minutes. The UI and analytics are capped at 8 updates per second. "Jump to day N" replays the run silently in 30-sim-minute ticks so the detectors still warm up.

Worth knowing: Health is derived from anomaly scores, not from the hidden severity. Once a fault persists, CUSUM saturates and that signal's health goes to ~0. So RUL extrapolates a detection-confidence curve, not a physical wear measurement. That's a common and reasonable proxy in PdM, but it's a proxy.
